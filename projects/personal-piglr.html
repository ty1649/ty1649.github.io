PIGLR

Skills Gained

Embedded Firmware Zephyr RTOS LTE-M / NB-IoT GNSS MQTT / TLS KiCad PCB Design Power Electronics Hardware Integration

Description

PIGLR is a pair of handheld, battery-powered devices that can locate each other outdoors and send a simple “bump” or ping.

3/3

finalizing overall requirements, acceptance tests, and communication packets required.

set up the acl file, created a new topic subscribe and deny channel, and added and built the loop in main.c.

the current pseudocode is basically:

INITIALIZATION:
    initialize LEDs, buttons, and flash storage
    load persistent variables from flash:
    bump_id, loc_seq, last_received_bump_id, next_gps_time

BOOT MODEM:
    provision TLS certificate
    register with LTE network
    request power saving mode from the tower

MAIN LOOP:
    check if LTE is still registered
    sync UTC time if needed for TLS

    connect to piglr.duckdns.org over TLS
    subscribe to "my bumps" and "peer location" topics

    open a short polling window
    wait and listen for incoming messages from the peer

    if a bump JSON arrives:
        parse the bump_id

        if bump_id > last_seen:
            accept the bump
            trigger haptics
            save the new last_seen value to flash

        otherwise:
            ignore it as a duplicate

    if the button was pressed while asleep:
        build the bump JSON
        publish it to the peer’s bump topic
        increment bump_id and save it to flash

    if enough time has passed since the last GPS update:
        run the GPS logic
        publish retained location JSON
        calculate and save next_gps_time

    disconnect MQTT
    reset or increment fail_count
    sleep

the overall idea is that the device wakes up every five minutes, connects, checks for stuff, does whatever it needs to do, and then sleeps again.

if something fails, it waits 60 seconds, 120 seconds, 300 seconds, etc. instead of instantly trying over and over.

location is published to:

pairs/<pair_id>/loc/<device_id>

and each device reads from the peer’s version of that topic.

location uses qos 0 and is retained, since the other device should be able to wake up and immediately get the latest known location.

bumps are sent to:

pairs/<pair_id>/bump/<target_device_id>

bumps use qos 1 and are not retained. each one has a bump_id so the receiving device can dedupe it instead of vibrating multiple times if mqtt redelivers something.

3/26

been a while, but i have mainly been working on the schematic.

i’ve done the hardware summaries and chosen the hardware. hopefully this is already half and i can finish by the end of april.

the current main hardware is:

  • ln60e840f main module
  • sharp ls027b7dh01 display
  • lis2mdl magnetometer
  • lis2dw12 accelerometer
  • drv2605l haptic driver
  • bq24074 charger and power path
  • max17048 fuel gauge
  • protected 1s lipo
  • tps63802 main 3.3 v buck-boost
  • external lte and gnss antennas
  • usb-c charging
  • tag-connect swd and uart pads for debugging

rev a is supposed to be a working prototype carrier board around the module. it is optimized for bring-up success, low integration risk, strong debug visibility, compact but not over-minimized layout, and preserving a path to later miniaturization.

basically, rev a is not trying to be the smallest final product. it just needs to be electrically robust, easy to debug, mechanically plausible, rf-aware, sensor-aware, and good enough to become a real working handheld prototype.

3/27, 2:00 am

should be pretty done with the schematic now, hopefully.

the main power path is:

USB-C 5 V
→ BQ24074 charger and power path
→ battery / VSYS
→ TPS63802 buck-boost
→ 3V3_MAIN

there is also a separate display power block because the sharp display needs an approximately 5 v panel rail while the logic stays in the 3.3 v domain.

one thing i changed was going from a normal buck regulator to a buck-boost. a buck-only setup was looking electrically marginal because VSYS can fall below 3.3 v during realistic battery operation and lte current bursts.

the buck-boost should keep the main 3.3 v rail regulated through that.

4/20

okay i really need to rethink everything.

i realized multiple things, such as how my current button configuration isn’t going to work because i need something like a pcb connected to the main pcb with the tactile buttons smt soldered onto there.

the biggest thing is that my c-shaped pcb around the battery isn’t going to work.

this is mainly due to the display fpc connector being too short. since i’m wrapping the cable around the main four-layer pcb anyway, it will only go around 1 mm above the pcb’s backside.

i also realized that the m.2 connector is shorter than expected. it is actually only around 2.5 mm above the pcb instead of 4.2 mm, and the module is also thicker on the side above the pcb.

this leaves not enough thickness for a 5–6 mm battery to fit under the display.

there are a couple solutions:

  1. display angled—not cool, but i can keep the current pcb shape
  2. make the whole thing thicker, around 15 mm. wondering how thick this actually feels, but this could fit a 500–1000 mah battery
  3. smaller battery. found some smaller ones, but they are closer to 150 mah
    • could also have an optional extra battery pack adapter, which attaches another battery in parallel to extend battery life

leaning toward number 3 unless i test-fit number 2 later and it actually feels good and 15 mm doesn’t feel too thick.

the rest of it is kind of wired. also had to fix a lot of solder-mask expansion issues and a lot of clearance errors.

i should really finish this even sooner. i wanted to have at least a day or two to test the stuff at formula using their oscilloscope, but i don’t think i’ll be able to make that timeline anymore rip.
